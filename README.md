This repository is a work-in-progress matching decompilation of **Shin Megami Tensei: Persona 3 FES** for the Sony PlayStation 2 (NTSC-U). It reconstructs the retail executable from split assembly, data, and C sources, then checks generated bytes against the original executable.

**This repo does not contain any assets or original code from the game's files; you need your own legally obtained copy of the game to build and run it.**

## Target executable

| Version | Executable | SHA-1 | Size |
| --- | --- | --- | --- |
| NTSC-U | `SLUS_216.21` | `3929cd7c02be944f25ec6b924e5f1eab9bc5e9cb` | 9,096,860 bytes |

The verified SHA-256 is `d1b163eb20cb72d8764d2b94a8751abfc9e82fce7ae9e692dfaf97d64e3957bc`; the verified MD5 is `9074ba25f5a100940ed233c9f8f675ab`.

The target is a stripped MIPS R5900 Emotion Engine ELF. The compiler is Metrowerks CodeWarrior for PS2, `mwccps2.exe` build `3.0.1b210-060308`.

## Quick start

Install Python 3.8 or newer, [splat64](https://github.com/ethteck/splat), and GNU MIPS little-endian binutils with R5900 support (`mipsel-linux-gnu-as` and `mipsel-linux-gnu-objcopy`). On Debian or WSL, the binutils package is `binutils-mipsel-linux-gnu`.

Install the CodeWarrior PS2 toolchain `mwcps2-3.0.1b210-060308`, including `mwccps2.exe` and `mwldps2.exe`. Use a Windows-native installation or run it under Wine or wibo.

Clone the repository and enter its directory:

```sh
git clone https://github.com/snaku/Persona3-FES-Decompilation.git
cd Persona3-FES-Decompilation
```

Create the ignored local configuration. Replace both placeholder paths with paths on your system:

```sh
cat > tools/verify_config.local.json <<'JSON'
{ "mwcc": "path/to/mwcps2-3.0.1b210-060308/mwccps2.exe",
  "retail_elf": "path/to/SLUS_216.21" }
JSON
```

Run the setup and build:

```sh
make setup
make split
make
```

For a per-file report, run `python tools/verify.py <file.c>`. The file must contain the function marker expected by the verifier.

## How progress is measured

`tools/verify.py` compares each function's compiled bytes against the retail executable and reports `MATCH`, `NONMATCHING`, `STUB`, or `SIZE_MISMATCH`.

The progress badges and generated objdiff report are authoritative. Run `python tools/progress.py` for the current report. Percentages are not copied into prose because they go stale.

## Glossary

- **window** — The byte range in the retail executable that a function occupies.
- **census** — An automated inventory pass over all functions.
- **gate** — An automated pass/fail check.
- **wall / floor** — A difference the compiler will not let source changes remove.
- **lever** — A source-level change that alters generated code.
- **residual** — The remaining byte difference for a function that does not yet match.
- **sweep** — A batch run over many functions.

## How the matching build works

```text
retail SLUS_216.21 ──extract──▶ image.bin
        │
   splat split (config/slus21621.yaml)
        ▼
   asm/*.s + data ranges
        │
        ├─ decompiled translation units ─ src/*.c ─▶ C objects
        │                                           (mwccps2)
        └─ remaining ranges ──▶ assembly objects
                                (mipsel-linux-gnu-as)
        ▼
   all objects ──mwldps2──▶ loadable image
        ▼
   splice into the retail ELF wrapper ──▶ build/SLUS_216.21
```

`tools/build.py` drives this pipeline; `make` is its thin wrapper. GNU `as` assembles the generated R5900 sources, while CodeWarrior compiles decompiled C and the original CodeWarrior linker places all objects.

Decompiled files link as real C objects rather than through a post-link byte overlay. `tools/recover_symbols.py` recovers cross-file symbol addresses from matched relocations, and `make symbols` writes `config/symbols_recovered.txt`. A fully decompiled translation unit can link its `.rodata`, `.data`, `.sdata`, `.sbss`, and `.bss` sections at recovered addresses. Files remain on the assembly baseline while their symbols or functions are still unresolved.

The complete build also checks the rebuilt image against the retail ELF. The per-function check masks relocated fields and checks tail padding.

`make setup` extracts the loadable image from the retail ELF. `make split` regenerates the splat assembly and data split after configuration changes.

The linker keeps real `%hi`/`%lo` and `jal` relocations so recovered symbols remain usable across objects. Data that is indistinguishable from code stays as retail words.

The rebuilt loadable image is spliced into the retail ELF wrapper only after linking. This keeps the wrapper and its metadata unchanged while the build checks the complete executable.

## Repository layout

```text
config/     splat config and symbol maps
tools/      build, split, verification, symbol, and report utilities
asm/        committed macros; generated assembly and chunks are ignored
src/        decompiled C
include/    headers and assembly macros
docs/       contributor notes and optional SDK symbol tools
build/      ignored build outputs, objects, and objdiff inputs
```

Optional SDK symbol matching and promotion are documented in [`docs/sdk-symbols.md`](docs/sdk-symbols.md).
